### 2026-11-24 — 1단계: 프로젝트 이해와 요구사항 분석

- 목표: 프로젝트의 목적, 사용자 권한, 게시판 유형, 기능·비기능 요구사항을 구분한다.
- 배운 점:
  - 자유게시판과 카드게시판은 화면뿐 아니라 콘텐츠 성격과 사용자 행동이 다르다.
  - 권한은 화면 노출뿐 아니라 API 실행 가능 여부와 데이터 변경 범위까지 제한한다.
  - 자유게시판은 목록 탐색에 적합한 페이지네이션을 사용하고, 카드게시판은 이미지 탐색 경험을 위해 무한 스크롤을 사용한다.
  - 학습 요구사항, 기능 요구사항, 비기능 요구사항은 서로 다른 관점의 기준이다.
- 확인 결과:
  - 게시판 유형을 학습 목적과 사업적 목적 관점에서 설명했다.
  - 사용자별 접근 차이를 설명했다.
  - 페이지네이션과 무한 스크롤의 사용 이유를 설명했다.
  - 기능 요구사항과 비기능 요구사항의 구분을 학습했다.
- 다음 학습: 게시판 도메인 객체와 데이터 관계를 식별한다.

### 2026-11-24 — 2단계: 도메인과 데이터 설계

- 목표: 게시판의 핵심 객체와 객체 간 관계를 식별한다.
- 배운 점:
  - User, Post, Comment, File은 역할·수명주기·적용 규칙이 다르므로 별도 객체로 분리할 수 있다.
  - 하나의 Post 구조를 공유하면 공통 기능의 유지보수는 쉬워질 수 있지만, 게시판별 특수 규칙을 표현하기 어려워질 수 있다.
  - 게시판 구조를 통합할지 분리할지는 객체의 역할·내용이 얼마나 일치하는지와 개별화 필요성을 기준으로 판단한다.
  - `parent_id`를 이용하면 댓글과 대댓글의 계층 관계를 표현할 수 있다.
  - 파일 본문은 별도 스토리지에 두고 데이터베이스에는 key·path 등 관리 정보를 저장하는 방식을 검토한다.
- 확인 결과:
  - 객체를 역할과 규칙의 차이로 분리하는 이유를 설명했다.
  - 통합 Post 구조의 장점과 한계를 설명했다.
  - 대댓글의 재귀적 관계를 설명했다.
  - 파일 저장소와 데이터베이스의 책임을 구분했다.
- 보완한 점:
  - 객체 분리는 역할뿐 아니라 식별자, 수명주기, 권한, 변경 빈도도 기준이 된다.
  - 파일 분리 시 업로드 실패, 삭제 시 고아 파일, 접근 권한과 데이터베이스 정합성을 함께 고려해야 한다.
- 다음 학습: 애플리케이션 구조와 API의 책임을 설계한다.

### 2026-11-24 — 3단계: 애플리케이션 구조와 API 설계

- 목표: 요청 처리 흐름과 계층별 책임, API 오류와 응답 계약을 이해한다.
- 배운 점:
  - 프론트엔드의 화면 요소 노출은 사용자 경험을 위한 제어이고, 실제 권한 검증은 백엔드가 수행해야 한다.
  - 인증은 사용자의 신원을 확인하는 과정이고, 인가는 인증된 사용자가 특정 작업을 수행할 수 있는지 판단하는 과정이다.
  - 목록·상세 API는 필요한 데이터와 사용 목적이 다르므로 분리할 수 있다.
  - API는 필요한 데이터만 조회·전달하여 DB 자원, 네트워크 비용, 클라이언트 노출 범위를 줄여야 한다.
  - 일정한 응답 형식은 클라이언트와 서버 사이의 계약이며, 개발·테스트·유지보수의 공통 기준이 된다.
- 확인 결과:
  - 서비스 계층에서 권한 검증을 수행해야 하는 이유를 설명했다.
  - 인증 실패와 인가 실패를 구분했다.
  - API 분리가 데이터 최소화·성능·보안과 관련된다는 점을 설명했다.
  - 응답 형식과 오류 상태를 계약으로 관리해야 하는 이유를 설명했다.
- 보완한 점:
  - FE의 접근 제어는 보안 장치가 아니라 UX 보조 수단이며, BE 검증이 최종 기준이다.
  - 인증 정보가 저장되는 위치와 인증 판단을 수행하는 주체는 인증 방식별로 구분해야 한다.
- 다음 학습: Node.js 런타임, 이벤트 루프, 모듈 시스템과 프로젝트 구성을 이해한다.

### 2026-11-26 — 1단계 실습: 첫 번째 수직 기능 선정

- 목표: 공통 요구사항에서 작은 구현 단위인 비회원 자유게시판 목록·상세 조회를 선정하고 완료 기준을 정의한다.
- 학습한 내용:
  - 목록 API는 query parameter, 상세 API는 path parameter를 중심으로 입력을 설계한다.
  - 응답 계약에는 HTTP 상태 코드, 애플리케이션 오류 코드, 응답 데이터 구조와 오류 형식을 포함할 수 있다.
  - 리소스가 없을 때는 HTTP 404와 애플리케이션 오류 코드 `NOT_FOUND`를 함께 사용할 수 있다.
  - 목록 정렬은 `CREATE_DATE` 또는 PK 하나만 사용하기보다 `CREATE_DATE DESC, ID DESC`처럼 보조 정렬 기준을 두어 결과를 안정화한다.
- 권한 범위 판단:
  - 첫 번째 수직 기능에서는 비회원 읽기 허용이라는 정책을 정의하고, 전체 인증·인가 시스템은 별도 단계에서 구현한다.
  - 첫 기능의 권한 처리는 전체 권한 시스템 구현이 아니라 조회 범위와 이후 확장 지점을 정하는 작업이다.
- 보완한 점:
  - API가 받는 데이터는 서버가 수신하는 전체 정보가 아니라 경로·쿼리·헤더·본문 등 요청 입력으로 구분해야 한다.
  - 생성일시는 동일할 수 있으므로 단독 정렬 기준으로 충분하지 않으며, DB insert 순서가 항상 전역 순서를 보장한다고 가정하지 않는다.
- 다음 학습: 첫 수직 기능에 필요한 도메인·데이터 구조를 설계한다.

### 2026-11-26 — 2단계 실습: 자유게시판 데이터 구조

- 목표: 첫 수직 기능에 필요한 최소 데이터 구조를 PostgreSQL에 반영한다.

  - `CREATE_DATE`, `ID` 기준 정렬 규칙을 정의했으며 보조 인덱스는 추후 정의하기로 했다.
  - 반복 실행 가능한 스키마 초기화와 테스트용 시드 데이터를 구성했다.
- 확인 결과:
  - PostgreSQL에 스키마와 시드 데이터가 정상 생성되었다.
  - 게시판 종류와 게시글 관계를 데이터 구조로 표현했다.
- 다음 학습: API 공통 처리와 계층별 책임을 보완한다.

### 2026-11-26 — 3단계 실습: API 기반 구조

- 목표: HTTP 요청을 검증하고 저장소 조회 결과를 일관된 JSON 응답으로 반환한다.
- 구현 내용:

  - 페이지·크기 입력 검증과 공통 JSON 응답을 구현했다.
  - 예외 발생 시 `500` 오류 응답을 반환하도록 구성했다.
- 상태: 부분 완료
- 보완할 점: 현재 라우팅과 업무 흐름이 `server.js`에 남아 있어 controller·service 계층 분리가 필요하다.
- 다음 학습: API 계층을 정리한 뒤 인증·인가와 회원 기능을 구현한다.

### 2026-11-26 — 4단계 실습: 자유게시판 조회

- 목표: 비회원 자유게시판 목록·상세 조회를 실제 데이터로 검증한다.
- 구현 내용:
  - `GET /api/boards/free/posts` 목록 API를 구현했다.
  - `GET /api/boards/free/posts/:postId` 상세 API를 구현했다.
  - 페이지네이션과 `CREATE_DATE DESC, ID DESC` 정렬을 적용했다.
  - 상세 조회 시 조회수를 증가시켰다.
  - 존재하지 않는 게시글은 `404 NOT_FOUND`로 반환했다.
- 확인 결과:
  - 목록 요청에서 `size=2`일 때 2건과 페이지 정보를 반환했다.
  - 상세 조회 시 조회수가 증가했다.
  - 잘못된 페이지는 `400 INVALID_PAGINATION`으로 반환했다.
  - 존재하지 않는 게시글은 `404 NOT_FOUND`로 반환했다.
- 시행착오:
  - 첫 구현에서 페이지 크기를 저장소의 `limit`으로 전달하지 않아 전체 게시글이 반환되었다.
  - 호출부와 저장소 함수의 인자 이름을 맞춘 뒤 재검증했다.
- 다음 학습: 인증·인가와 회원 기능을 구현한다.

### 2026-11-26 — DB 구성 책임 정정

- 정정 내용: 테이블·컬럼·초기 데이터 생성은 공통 `database` branch의 `database/v1/sql/`에서 관리한다.
- Node.js 책임: 실행 중인 PostgreSQL에 연결하고 애플리케이션 조회·변경 SQL을 실행한다.
- 제거한 구현: Node.js의 `db:init` 스크립트와 Node.js 내부의 스키마·시드 데이터 실행 코드.
- 이유: 여러 스택이 동일한 데이터 구조를 공유해야 하며, 특정 스택이 공통 DB 구성을 소유하지 않도록 하기 위해서다.
