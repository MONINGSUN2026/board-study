# 개발 계획

이 문서는 `board-study` 프로젝트의 실제 개발 범위와 진행 순서를 관리한다.

## 1. 개발 목표

- 공통 게시판 요구사항을 Node.js API 서버로 구현한다.
- 자유게시판과 카드게시판의 기능·데이터·화면 접근 차이를 분리한다.
- 설계, API, 데이터베이스, 인증·인가, 파일 처리, 테스트, 배포까지의 개발 흐름을 연결한다.
- 다른 기술 스택에서 동일한 요구사항을 비교 구현할 수 있는 기준을 만든다.

## 2. 기준 문서

- `docs/common/requirements.md`: 비즈니스 요구사항
- `docs/common/features.md`: 공통 기능 목록
- `docs/common/database.md`: 로컬 데이터베이스와 연결 정보
- `docs/nodejs/decisions.md`: Node.js 기술 결정 기록

## 3. 개발 범위 상세

### 3.1 사용자와 권한

- 비회원은 게시글과 댓글을 조회할 수 있다.
- 회원은 자신의 게시글과 댓글을 작성·수정·삭제할 수 있다.
- 관리자는 모든 게시글·댓글·회원에 대한 관리 권한을 갖는다.
- 관리자는 부적절한 게시글·댓글을 삭제하고 회원을 차단할 수 있다.
- 권한 검증은 화면 노출 여부와 별개로 API 서버에서 최종 처리한다.

### 3.2 게시판 유형

#### 자유게시판

- 텍스트 중심의 테이블형 목록을 제공한다.
- 한 페이지에 정해진 수의 게시글만 반환한다.
- 카테고리와 태그 필터를 제공한다.
- 최신순·조회순·추천순 정렬을 제공한다.
- Offset 기반 페이지네이션을 사용한다.
- 게시글 상세 조회 시 조회수를 증가시킨다.

#### 카드게시판

- 이미지 중심의 카드형 목록을 제공한다.
- 카드에는 필수 썸네일, 제목, 작성자, 조회수, 작성일을 포함한다.
- 카테고리와 태그는 사용하지 않는다.
- 게시글 작성 시 썸네일 이미지 1개 이상과 다중 이미지를 지원한다.
- 목록은 최신순으로 조회하고 한 번에 12개를 반환한다.
- 무한 스크롤을 지원할 수 있도록 Cursor 기반 페이지네이션을 사용한다.
- 카드 클릭 시 별도 상세 조회를 제공한다.

### 3.3 게시글·댓글 기능

- 자유게시판과 카드게시판의 게시글 작성·조회·수정·삭제를 제공한다.
- 게시글 작성자는 자신의 게시글만 수정·삭제할 수 있다.
- 관리자는 다른 사용자의 게시글도 관리할 수 있다.
- 댓글과 대댓글을 지원한다.
- 대댓글은 `parent_id` 등 부모 댓글 관계를 유지한다.
- 댓글의 작성자·관리자별 수정·삭제 권한을 구분한다.
- 게시글과 댓글의 삭제 시 종속 데이터 처리 정책을 정의한다.

### 3.4 홈·검색·탐색

- 홈 경로는 `/`로 제공한다.
- 자유게시판 경로는 `/board/free`로 제공한다.
- 카드게시판 경로는 `/board/card`로 제공한다.
- 홈에는 최근 1개월 이내 자유게시판 인기글 5개를 제공한다.
- 인기글은 조회수 내림차순으로 정렬하고, 동률이면 최신순으로 정렬한다.
- 홈에는 카드게시판 카드 그리드와 무한 스크롤 진입점을 제공한다.
- 검색은 카드게시판에만 제공한다.
- 자유게시판은 검색하지 않고 카테고리·태그 필터와 정렬을 제공한다.

### 3.5 회원·파일·관리 기능

- 회원가입·로그인·로그아웃을 제공한다.
- 비밀번호는 평문으로 저장하지 않고 해시하여 저장한다.
- 게시글에 이미지를 첨부하고 파일을 다운로드할 수 있어야 한다.
- 파일 크기·확장자·MIME 유형을 검증한다.
- 실제 파일은 별도 저장소에 보관하고 DB에는 메타데이터와 관리 키를 저장한다.
- 카드게시판 이미지는 필요 시 썸네일을 생성한다.
- 관리자는 공지사항을 작성하고 상단 고정할 수 있다.

### 3.6 비기능 범위

- SQL Injection, XSS, CSRF 등 기본 공격을 방어한다.
- 대량 데이터 조회를 고려해 페이지네이션과 인덱스 후보를 정의한다.
- 조회수·인기글과 같은 조회 중심 기능은 캐싱 적용 가능성을 검토한다.
- 환경변수, 마이그레이션, 로깅, 헬스 체크, 실행 절차를 운영 기준에 맞게 문서화한다.

## 4. 구현 원칙

- 요구사항을 작은 수직 기능으로 나누고, 한 기능을 설계부터 검증까지 연결한다.
- API 서버가 권한을 최종 검증한다.
- API는 필요한 데이터만 반환한다.
- 데이터베이스 연결은 애플리케이션 프로세스에서 재사용하는 Pool을 사용한다.
- 일반 쿼리는 Pool을 사용하고, 트랜잭션은 하나의 client를 대여해 처리한다.
- 사용자 입력값은 파라미터 바인딩으로 전달한다.
- 목록 조회는 안정적인 정렬 기준과 페이지네이션을 함께 정의한다.
- 실제 파일과 파일 메타데이터를 분리한다.
- 개발 단위의 의사결정 회의는 `docs/nodejs/meetings/`에 기록한다.

## 5. 개발 단계

### 1단계. 요구사항과 기능 계약

범위:

- `docs/common/requirements.md`와 `docs/common/features.md`를 기준으로 기능 범위를 확정한다.
- 사용자 유형과 기능별 권한을 확정한다.
- 자유게시판과 카드게시판의 차이를 기능·응답·접근 방식으로 정리한다.
- API별 입력·출력·오류·권한 계약을 정의한다.
- 기능별 완료 기준과 정상·실패 시나리오를 작성한다.

완료 기준:

- 공통 요구사항과 Node.js 구현 범위가 연결되어 있다.
- 구현하지 않을 항목과 후순위 항목이 구분되어 있다.
- 각 API의 요청·응답·권한·오류 조건을 설명할 수 있다.

### 2단계. 도메인·데이터 설계

범위:

- User, Board, Post, Comment, File의 책임과 관계를 정의한다.
- 자유게시판과 카드게시판의 공통 필드와 전용 필드를 구분한다.
- 댓글·대댓글의 부모 관계와 삭제 정책을 정의한다.
- 파일 메타데이터와 실제 파일 저장소의 책임을 분리한다.
- ERD와 데이터 제약조건을 정리한다.
- 목록·검색·인기글 조회에 필요한 인덱스 후보와 정렬 기준을 정의한다.
- 트랜잭션이 필요한 변경 작업과 일관성 기준을 정의한다.

완료 기준:

- 기능 요구사항에서 데이터 구조를 도출할 수 있다.
- 게시글·댓글·파일의 종속관계와 삭제 정책이 정의되어 있다.
- 각 주요 조회 API가 필요한 테이블·필드·정렬 기준을 갖는다.
- 데이터베이스 스키마와 애플리케이션의 책임 경계가 분리되어 있다.

### 3단계. 애플리케이션 기반

범위:

- 실행 스크립트
- 환경 설정
- HTTP 서버
- 헬스 체크
- 오류 응답 기본 형식
- graceful shutdown

완료 기준:

- 새 환경에서 설치와 실행이 가능하다.
- `/health`가 정상 응답한다.
- 종료 신호를 받으면 HTTP 서버와 DB Pool을 정리한다.

### 4단계. 자유게시판 조회

범위:

- 자유게시판 목록 조회
- 게시글 상세 조회
- 페이지 번호·크기 검증
- 최신순·조회순·추천순 정렬
- 카테고리·태그 필터
- 조회수 증가
- 존재하지 않는 게시글 처리

완료 기준:

- 비회원이 목록과 상세를 조회할 수 있다.
- 잘못된 페이지 요청은 일관된 오류 응답을 반환한다.
- 목록과 상세 응답에 필요한 데이터만 포함한다.
- 조회수 증가와 상세 조회가 같은 데이터 기준으로 동작한다.
- 정렬과 필터 조건이 API 계약과 일치한다.

### 5단계. 인증·인가

범위:

- 회원가입
- 로그인·로그아웃
- 인증 상태 확인
- 사용자·관리자 권한 구분
- 게시글 소유권 검증

완료 기준:

- 인증되지 않은 사용자의 보호 API 접근을 차단한다.
- 인증된 사용자라도 권한이 없으면 변경 요청을 거부한다.
- 인증 실패와 인가 실패를 구분한다.
- 비밀번호와 인증 정보가 안전하게 저장·전달된다.

### 6단계. 자유게시판 쓰기와 댓글

범위:

- 게시글 작성·수정·삭제
- 댓글 작성·수정·삭제
- 대댓글
- 작성자·관리자별 권한 규칙
- 게시글과 댓글의 삭제 정책

완료 기준:

- 권한 없는 변경을 차단한다.
- 게시글·댓글·대댓글의 종속관계를 유지한다.
- 변경 작업의 트랜잭션 경계를 정의한다.

### 7단계. 카드게시판과 파일

범위:

- 카드형 게시글 목록
- 카드게시글 작성·수정·삭제
- 카드게시글 상세 조회
- 이미지 중심 응답
- 무한 스크롤용 Cursor 페이지네이션
- 한 번에 12개 반환
- 필수 썸네일 검증
- 다중 이미지 업로드
- 파일 업로드·다운로드
- 파일 메타데이터 관리
- 저장소와 DB 불일치 정리

완료 기준:

- 자유게시판과 카드게시판의 요구사항을 구분한다.
- 카드게시글 작성·상세·목록 흐름이 연결된다.
- 허용하지 않은 파일의 업로드를 차단한다.
- DB에는 파일 관리정보를 저장하고 실제 파일은 별도 저장소로 관리한다.
- 중복·누락 없는 Cursor 조회를 제공한다.

### 8단계. 홈·검색·탐색

범위:

- 홈 인기글
- 최근 1개월 이내 자유게시판 인기글 5개
- 조회수 내림차순·동률 시 최신순 정렬
- 카드게시판 검색
- 자유게시판 카테고리·태그 필터
- 홈·게시판 라우팅 연결

완료 기준:

- 인기글 정책을 명확히 정의한다.
- 카드게시판만 검색하고 자유게시판은 필터·정렬만 제공한다.
- 조회 조건에 맞는 데이터만 반환한다.

### 9단계. 테스트·보안·운영

범위:

- API 통합 테스트
- 핵심 서비스 단위 테스트
- 인증·인가 테스트
- SQL Injection·XSS·파일 검증
- 로그·헬스 체크·오류 추적
- Pool과 DB 연결 상태 점검

완료 기준:

- 정상·실패·권한 경로를 자동 검증한다.
- 테스트가 개인 환경이나 실행 순서에 의존하지 않는다.
- 민감정보가 저장소에 포함되지 않는다.
- DB 연결 실패와 외부 저장소 실패를 진단할 수 있다.

### 10단계. 배포·회고

범위:

- 실행·빌드·테스트 명령 정리
- 환경별 설정 분리
- 데이터베이스 적용 절차 정리
- 배포와 배포 후 헬스 체크
- 개발 결과와 다음 스택 비교

완료 기준:

- 다른 환경에서 동일한 절차로 실행할 수 있다.
- 배포 실패와 데이터 변경 실패의 대응 방법을 설명할 수 있다.
- 재사용할 기준과 개선할 기준을 구분한다.

## 6. 개발 단계 완료 절차

각 단계는 다음 순서로 완료한다.

1. 단계의 요구사항과 완료 기준을 확인한다.
2. 설계와 API 계약을 정한다.
3. 구현 범위와 변경 단위를 확정한다.
4. 코드를 작성하고 실행 환경에 반영한다.
5. 정상·실패·권한 시나리오를 검증한다.
6. 구현 중 결정과 변경 사유를 문서에 기록한다.
7. 변경 단위와 commit·push·PR 범위를 확정한 뒤, 저장소 작업 규칙과 사용자 지시에 따라 반영한다.

## 7. 제외 범위

- Node.js 코드에서 공통 테이블 생성·초기 데이터를 자동 실행하지 않는다.
- 현재 요구사항과 무관한 대규모 리팩터링을 먼저 진행하지 않는다.
- 자유게시판과 카드게시판을 하나의 요구사항으로 억지로 통합하지 않는다.
- 인증·인가를 화면 노출만으로 처리하지 않는다.
- 파일 전체를 관계형 DB에 저장하지 않는다.
