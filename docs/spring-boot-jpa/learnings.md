# spring-boot-jpa — 학습 기록 (Learnings)

학습 중 논의·깨달은 내용과 나의 이해를 기록한다.

## 1. API 설계 원칙 (배운 것)

### Base URL / MSA
- MSA는 **도메인(기능) 단위**로 서비스를 나누고, API Gateway가 path prefix로 라우팅한다.
- URL에는 **구현 기술이 아닌 도메인/서비스 식별자**를 담는다(실무 관례).
- 이 프로젝트는 학습 단위(스택) 구분이 목적이므로 `/api/boot-jpa/v1`을 채택했다.

### API 분리 기준
- **화면(페이지) 기준이 아니라 리소스(데이터) 기준**으로 API를 나눈다.
- 권한은 각 리소스의 속성으로 부여한다.
- 화면(홈 등)은 여러 API를 조합해 구성하여 **재활용 + 책임분리**를 얻는다.

### Offset vs Cursor
- **Offset**: 지정 개수만큼 건너뛰기. 페이지 번호 이동 가능하지만 중간 삽입/삭제에 취약하고 깊은 offset은 느리다.
- **Cursor**: 마지막 항목 기준으로 이후 데이터를 조회. 무한스크롤에 적합하고 중간 변경에 안정적이다.

### D/E 분리 재고
- "단건/변경 vs 다건/조회"로 나누는 것은 인위적이다.
- 실무에서는 게시글 CRUD와 목록·검색이 **같은 "게시판" 도메인** 하나다 → D/E를 병합했다.

### JWT
- stateless 인증. 서버는 세션 저장 없이 서명 검증만 수행한다.
- 클라이언트가 `Authorization: Bearer <token>`으로 매 요청 전달한다.

## 2. 나의 이해

- API 목록 단계에서 남겨야 할 정보
  - 어떤 API가 필요한지 **명시적으로 목록화**
  - **API 공통 구조** 정의 (Base URL, 인증, 응답/에러 포맷)
  - **페이지네이션·정렬** 등 일부 규칙 (+ 권한)
- API 분리는 **페이지 구분보다 권한과 데이터를 우선**으로 한다.
- 홈은 한 화면에서 **여러 API를 호출**할 수 있으며, 이는 재활용·책임분리 원칙에 부합한다.
- offset(건너뛰기)과 달리, cursor는 **"마지막 항목 이후부터"**를 가리키는 무한스크롤 방식임을 이해했다.

## 3. 이번 논의로 확정된 사항

- Base URL: `/api/boot-jpa/v1`
- 인증: JWT
- 영역: A 공통 / B 인증·인가 / C 관리자 / D 게시판 (기존 D+E 병합)
- API 분리 기준: 리소스(데이터) 단위
